claude-discord-agent

A local, asynchronous job controller that connects Discord to Claude Code. You send a request from Discord; a Controller session dispatches it; Workers run claude -p; a non-LLM Supervisor guarantees you hear back. This page is the human-oriented overview — the precise contracts live in docs/architecture.md.

Roles and trust boundaries

RoleWhat it doesDiscord token
Controller Interactive Claude Code session with the Discord channel plugin. Accepts requests, dispatches jobs, replies with collected results. Never edits code itself. Via its channel plugin
Orchestrator daemon Single supervised process running the job queue, retry/backoff, Worker monitoring, and final delivery. Yes (Supervisor fallback)
Worker One claude -p run per job inside the registered repository. Prints a structured result block. Never

How you always hear back

When a job reaches a terminal state, the Supervisor makes sure exactly one notification happens even if the Controller session is dead:

  1. Wake (experimental, opt-in) — if a Controller tmux pane is registered and provably idle, type a one-line instruction into it: collect the result, reply on Discord, then report-done. Unknown pane state = do nothing (fail-closed).
  2. Fallback (default) — claim the job atomically and post a notification directly to the Discord API. By default it contains no Worker output; --fallback-result-preview opts into a 200-character redacted preview.

report-done after a successful reply suppresses duplicate delivery; transient API failures retry, permanent ones mark the job undeliverable.

Running it

PieceReference shape
Runtimeuv tool install git+<repo-url> → orchestrator. For source installs, pass --reinstall to pick up local changes when the version number is unchanged.
Daemonorchestrator daemon start --foreground under a process supervisor with keep-alive (launchd, systemd). The self-forking mode is for manual, unsupervised use.
ControllerA Claude Code session with the Discord channel plugin, inside tmux, wrapped in a restart loop and watched by a periodic health check.
SecretsDISCORD_BOT_TOKEN via environment or an owner-only (0600) credential file; state dirs are 0700. Hardened reads reject symlinks, foreign owners, and group/world-readable files.
One gateway connection per bot token. The Discord channel plugin connects to the Discord gateway once per MCP-server instance, unconditionally. If any other process holds a connection on the same token (another agent session, an IDE-embedded MCP client, an orphaned server), the newer login fails at startup and the host marks the plugin failed — the Controller then looks healthy but receives nothing. Health checks must verify the session's Discord MCP child process exists (with a startup grace period), and treat competing connections as faults to remove, not background noise.

Where things live

PathContentsMode
$XDG_STATE_HOME/claude-discord-agent/ state.db (authoritative), daemon.pid, daemon.log, controller.pane 0700 / 0600
$XDG_CONFIG_HOME/claude-discord-agent/ env (credentials), repos.json (export) 0700 / 0600

The daemon detaches by replacing file descriptors 0/1/2 (dup2), so starting it never blocks a calling pipeline, and everything it logs — including crash tracebacks — lands in daemon.log.
